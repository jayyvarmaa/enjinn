1.3 Abstract

This project presents the design and implementation of a custom 2D/3D game engine built in C++17 with a strong emphasis on runtime control, modular architecture, and memory-aware system design. Instead of relying on monolithic commercial engines, the project develops an internal architecture where gameplay modules are compiled as dynamically loaded containers and executed under an engine-managed runtime.

The engine addresses key challenges commonly hidden in prebuilt engines: deterministic update-loop control, explicit memory ownership and allocator binding, custom rendering integration for both 2D and 3D workloads, and runtime extensibility through DLL-based hot-reload workflows.

From the analyzed codebase, the core technical stack includes OpenGL (via GLAD), GLFW, Dear ImGui (docking branch), GLM, Box2D, stb_image/stb_truetype, and additional internal subsystems for profiling, serialization, diagnostics, and plugin-style gameplay containers. The architecture combines a runtime container manager, a scene graph (Node-Component model), component serialization, and custom memory utilities such as a free-list allocator and container memory arena.

The resulting system functions as both an execution runtime and an editor-enabled development environment, allowing iterative gameplay development, container-level isolation, and practical experimentation with rendering, physics, AI/behavior, animation, and tooling pipelines.

2. System Analysis

2.1 Introduction and Objectives

Introduction

The project implements a modular game engine intended to support both 2D and 3D interactive applications. The runtime initializes graphics, window, and input systems, loads gameplay logic from a DLL contract, and continuously executes container instances through a managed update cycle.

The architecture includes:

  1. Runtime-driven container lifecycle management.
  2. Scene-graph-based object modeling with component composition.
  3. Editor-facing windows and diagnostics systems.
  4. Custom memory and serialization infrastructure.

Objectives

  1. Build a full C++ game-engine runtime with explicit system ownership and update flow.
  2. Support both 2D and 3D rendering paths through OpenGL-based libraries.
  3. Enable modular gameplay through hot-swappable container contracts.
  4. Provide editor and diagnostics capabilities for development-time visibility.
  5. Integrate custom and semi-custom memory handling mechanisms to reduce uncontrolled heap usage.
  6. Support scene persistence and component serialization for reproducibility.
  7. Demonstrate practical subsystem breadth (physics, animation, AI, scripting, particles, profiling).

Functional Requirements

  2. The runtime shall load gameplay DLL exports and query available containers.
  3. The runtime shall instantiate and update one or more containers.

  6. The system shall serialize and deserialize scene/component state.

  3. vcpkg dependency setup.
  4. OpenGL-capable drivers and GLAD initialization support.
  5. GLFW runtime support.
  6. Dear ImGui docking branch integration.
  7. GLM, Box2D, and stb libraries.
  8. Windows runtime APIs for several runtime/editor code paths.

Hardware Requirements (Practical)

  1. x64 multi-core CPU.
  2. Minimum 8 GB RAM (16 GB recommended for 3D/editor workflows).
  3. GPU supporting OpenGL rendering pipeline.
  4. Storage for source, assets, and generated binaries.
  5. Keyboard/mouse input (gamepad optional and supported).

3. System Design

3.1 Modularization of the Engine

The EnJinn architecture is organized into multiple independent but cooperating modules. The folder structure and compile targets show a clear split between runtime, editor, shared systems, and gameplay modules.

ModulePrimary ResponsibilityDesign Role
core/enjinnRuntimeMain engine loop, DLL/container loading, update scheduling, runtime servicesExecution backbone
core/enjinnEditorEditor windows (hierarchy, inspector, scene view, diagnostics, tools)Development UI layer
core/sharedRuntimeCommon contracts (Container, Scene, Node, Component, AssetManager, window state)Shared domain model
core/enjinnSTDLow-level utility layer: allocators, static containers, file and path helpersInfrastructure utility layer
gameplayContainer implementations loaded via DLL (Mario, ThreeDTest, labs, examples)Application/plugin layer

This modularization allows the runtime to remain stable while gameplay modules evolve independently. It also supports hot-reload and per-container resource control, which is a strong systems-level choice for iterative game development.

3.2 Data Integrity and Constraints

  1. Container-level memory constraints are declared via ContainerStaticInfo (heap size, bonus allocators, FBO/UI needs).
  2. Scene graph integrity is maintained through parent-child ownership and recursive update/render traversal.
  3. Component allocation uses a fixed-size pool with overflow fallback, reducing fragmentation for normal component sizes.
  4. Serialization boundaries are explicit through serialize and deserialize methods in Node and Component derivatives.
  5. Runtime allocator binding around container updates enforces memory realm separation between engine and gameplay code.

3.3 Object-Oriented Design Principles Used

Inheritance

The design uses inheritance for engine extension points. Container is an abstract base type; gameplay modules implement create, update, and destruct. Similarly, Component is the base type and concrete systems such as GenericSpriteComponent, GenericPhysicsComponent, CameraComponent, and ScriptComponent derive from it.

Polymorphism

Runtime polymorphism appears in two key loops: the container update dispatch (calling each container through base pointer) and scene traversal (calling component virtual methods during onUpdate and onRender). This enables the engine to execute heterogeneous gameplay and component logic through uniform contracts.

Encapsulation

Subsystems encapsulate state and responsibilities: Shader caches uniform locations internally; ContainerManager owns container lifecycle; EnJinnWindow centralizes input/window state; ComponentPool hides allocation mechanics.

Abstraction

Engine-facing interfaces abstract platform and API details. Gameplay code receives RequestedContainerInfo, Input, and WindowState rather than direct runtime internals. This keeps gameplay modules focused on logic, with memory and runtime orchestration handled by the core.

3.4 User Interface Design (Editor GUI)

The editor is implemented using Dear ImGui (docking branch). The editor class aggregates multiple specialized windows: hierarchy, inspector, scene view, profiler, material editor, build window, and diagnostics. The design follows a tool-window paradigm suitable for engine development: live diagnostics, scene inspection, and runtime control in one frame-driven interface.

Diagnostic and lab windows indicate a usability focus on subsystem verification. Runtime containers can also request ImGui framebuffers and IDs, allowing integrated tool and gameplay views.

4.1 Crucial Code Snippet 1: Runtime Main Loop

File: EnJinn/core/enjinnRuntime/enjinnMain.cpp (runtime orchestration loop) 
while (!shouldClose)
{
    if (window.shouldClose())
    {
        shouldClose = true;
        break;
    }

    enjinn::enjinnImgui::imguiStartFrame(window.context);
    glClear(GL_COLOR_BUFFER_BIT);

#if !ENJINN_SHOULD_REMOVE_EDITOR
    editor.update(window.input, shortcutManager, logs,
        pushNotificationManager, loadedDll, containerManager, imguiIdsManager);
#endif

#if !(ENJINN_SHOULD_REMOVE_EDITOR)
    if (editor.shouldReloadDll)
    {
        editor.shouldReloadDll = false;
        containerManager.reloadDll(loadedDll, window, logs);
    }

    containerManager.update(loadedDll, window, logs, imguiIdsManager, &editor.consoleWindow);
#else
    containerManager.update(loadedDll, window, logs, imguiIdsManager, nullptr);
#endif

    enjinn::enjinnImgui::imguiEndFrame(window.context);
    window.update();
    shortcutManager.update(window.input);
}

This loop shows a layered execution pipeline: frame begin, editor pass, container pass, frame end, and IO/state updates. The design keeps tooling and gameplay synchronized within one deterministic cycle. Runtime reload logic is handled in-loop, minimizing restart cost during development.

4.2 Crucial Code Snippet 2: Allocator Binding Around Container Update

File: EnJinn/core/enjinnRuntime/containerManager/containerManager.cpp (per-container update wrapper) 
loadedDll.bindAllocatorDllRealm(&c.second.allocator);
bool rez = c.second.pointer->update(windowInput, windowState, c.second.requestedContainerInfo);
loadedDll.resetAllocatorDllRealm();

This is one of the most important architectural points in the codebase. Every container update executes under its own allocator context. It reduces accidental cross-realm allocation patterns and helps diagnostics/snapshot systems. The explicit reset call immediately after update prevents allocator leakage into runtime code paths.

4.3 Crucial Code Snippet 3: Component Pool Allocation Strategy

File: EnJinn/core/sharedRuntime/sceneGraph/node.h (ComponentPool) 
void* allocate(size_t size)
{
    size = (size + 15) & ~15;

    if (size > MAX_ALLOC || offset + size > POOL_SIZE)
    {
        return std::malloc(size);
    }

    void* ptr = pool + offset;
    offset += size;
    return ptr;
}

void deallocate(void* ptr)
{
    if (ptr >= pool && ptr < pool + POOL_SIZE)
    {
        return;
    }
    std::free(ptr);
}

This snippet demonstrates a pragmatic hybrid allocator: fixed pool for common component sizes and heap fallback for overflow cases. Alignment is explicit. Deallocation avoids per-object pool reclamation and instead supports fast reset semantics, which suits frame/update-oriented component workloads.

4.4 Crucial Code Snippet 4: Shader Uniform Location Caching

File: EnJinn/core/enjinnRuntime/rendering/material.cpp (Shader class) 
int Shader::getUniformLocation(const std::string& name)
{
    auto it = uniformLocations.find(name);
    if (it != uniformLocations.end())
    {
        return it->second;
    }

    int loc = glGetUniformLocation(programID, name.c_str());
    uniformLocations[name] = loc;

    return loc;
}

bool Shader::compileShader(unsigned int shaderID, const std::string& source, const std::string& type)
{
    glCompileShader(shaderID);

    GLint success;
    glGetShaderiv(shaderID, GL_COMPILE_STATUS, &success);

    if (!success)
    {
        std::cerr << "Shader compilation failed (" << type << "): " << getCompilationErrors(shaderID) << std::endl;
        return false;
    }

    return true;
}

This code improves rendering efficiency by caching uniform lookups instead of repeatedly querying OpenGL. It also includes immediate shader compile-status checks and error reporting, improving diagnosability of pipeline failures.

5. Code Quality Discussion

5.1 Code Standardization Practices

  1. Consistent subsystem foldering and header-based API boundaries.
  2. Engine-prefixed macros and compile-time feature flags for development vs production behavior.
  3. Stable interface contracts for containers and components.
  4. Separation between runtime-side orchestration and gameplay-side implementation.

5.2 Efficiency Techniques

  1. Component pool allocation and alignment for common small objects.
  2. Per-container allocator binding to localize allocation costs and control memory domains.
  3. Uniform location caching in shader system.
  4. Frame timing aggregation per container for lightweight performance monitoring.
  5. CMake interprocedural optimization enabled at project level.

5.3 Error Handling Techniques

  1. Assertion guards for critical initialization steps (GLFW/GLAD/DLL load).
  2. Boolean return-based checks for creation/update/load operations.
  3. Shader compilation/link diagnostics through explicit status checks and logs.
  4. Fallback behaviors in allocator and file-load paths to avoid immediate catastrophic failure in non-critical paths.

5.4 Parameter Passing Methods

  1. Heavy or mutable structures passed by reference where orchestration is required (for example RequestedContainerInfo and manager objects).
  2. Frame input/window-state are passed explicitly to update calls, maintaining deterministic frame context.
  3. Const references used in several rendering/material APIs to avoid unnecessary copies.
  4. Function pointers and callback signatures are used for DLL interface boundaries and file-opener bindings.

Overall, the codebase reflects an engine-oriented C++ style emphasizing clear subsystem contracts, explicit runtime control, and pragmatic performance-conscious implementation.
