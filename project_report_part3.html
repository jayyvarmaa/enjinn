6. Testing and Quality Assurance

6.1 Testing Strategy Overview

Given the complexity of a game engine spanning rendering, physics, scene management, and editor tooling, testing is structured in concentric layers: unit testing for mathematical foundations, integration testing for subsystem interactions, system testing for end-to-end gameplay, and manual testing for visual and gameplay correctness.

Test Pyramid

               /\
              /  \     System & Visual Tests
             /    \    (Manual, gameplay scenarios)
            /------\
           /        \   Integration Tests
          /          \  (Subsystem interaction)
         /            \
        /              \ Unit Tests
       /________________\ (Math, allocators, containers)

6.2 Unit Testing

6.2.1 Memory Allocator Unit Tests

Critical for engine stability. Unit tests should verify:

  1. Basic Allocation & Deallocation: Allocate blocks of various sizes (8 bytes to 1 MB), verify returned pointers are within heap bounds and properly aligned.
  2. Fragmentation Handling: Allocate and free in alternating patterns; verify free-list coalescing reduces fragmentation.
  3. Guard Value Detection: Deliberately corrupt guard values around allocated blocks; verify assertions trigger.
  4. Double-Free Detection: Attempt to free same pointer twice; verify guard value check catches it.
  5. Boundary Conditions: Allocate exactly at heap limits, allocate 0 bytes (edge case), allocate more than available.
Sample Unit Test Case (Pseudocode): 
TEST_CASE("FreeListAllocator - Basic Allocation") {
    char buffer[1024];
    FreeListAllocator alloc(buffer, sizeof(buffer));
    
    void* p1 = alloc.allocate(100);
    REQUIRE(p1 != nullptr);
    REQUIRE(p1 >= buffer && p1 < buffer + sizeof(buffer));
    
    void* p2 = alloc.allocate(50);
    REQUIRE(p2 != nullptr);
    REQUIRE(p2 > p1);  // subsequent allocation higher in memory
    
    alloc.free(p1);
    alloc.free(p2);
    
    void* p3 = alloc.allocate(150);
    REQUIRE(p3 == p1);  // memory reused after free
}

6.2.2 Component Pool Allocation Tests

  1. Fixed-Pool Allocation: Allocate components within pool size limits; verify bump-pointer behavior.
  2. Fallback to Malloc: Allocate components exceeding MAX_ALLOC; verify malloc is used.
  3. Alignment Verification: Allocate various sizes; verify 16-byte alignment enforced.
  4. Pool Reset Semantics: After frame, reset pool offset; verify next allocations start fresh.

6.2.3 Mathematics Library Tests (GLM Integration)

  1. Vector Operations: Test addition, subtraction, dot product, cross product for 2D/3D vectors.
  2. Matrix Transformations: Verify matrix multiplication, inverse, transpose, and perspective/orthogonal projection.
  3. Quaternion Rotations: Test quaternion composition, slerp, conversion to matrix form.
  4. Numerical Stability: Test edge cases (very small/large values, near-zero divisions).

6.3 Integration Testing

6.3.1 Scene Graph Integration

  1. Create a scene with 10+ nested nodes; add diverse components (sprite, physics, camera).
  2. Update transforms with delta-time; verify child nodes inherit parent transforms correctly.
  3. Serialize/deserialize scene; verify all component data persists.
  4. Add/remove children during update; verify no dangling pointers.

6.3.2 Container Lifecycle

  1. Load a gameplay container DLL; verify export resolution succeeds.
  2. Create container instance with explicit allocator binding; verify allocator is bound before update, unbound after.
  3. Update container multiple frames; verify memory usage stays within declared bounds.
  4. Reload DLL while container is running; verify old state is preserved or reset as intended.
  5. Destroy container; verify all resources are cleaned up and allocator is reset.

6.3.3 Rendering Pipeline

  1. Create shader with vertex/fragment source; verify compilation succeeds.
  2. Query uniform locations; verify caching works (second lookup returns cached value).
  3. Set uniform values and render quad; verify visual output matches expected result.
  4. Test shader compilation failure path; verify error logged and fallback shader used.

6.5 Debugging and Code Improvement

6.5.1 Debugging Techniques

  • Assertion-Driven Development: ENJINN_PERMA_ASSERT macros catch invariant violations early (e.g., uninitialized allocator, guard value corruption).
  • Logging and Diagnostics: Subsystems log initialization, error conditions, and performance metrics. Logs are aggregated in editor console window.
  • Visual Diagnostics: ImGui windows provide real-time inspection of scene hierarchy, component properties, profiler data, and allocator metrics.
  • Breakpoint Integration: VS Code/Visual Studio debuggers can attach to running engine; breakpoints in gameplay code are fully functional.
  • Memory Snapshot: Calculate available/fragmented memory via calculateMemoryMetrics(); report in diagnostics window.

6.5.2 Code Improvement Workflow

  1. Profiling: Measure frame time by subsystem (editor, containers, rendering). Identify bottlenecks.
  2. Optimization Targets:
    • Shader uniform caching reduced per-frame glGetUniformLocation calls.
    • Component pool allocation reduced fragmentation for small components.
    • Per-container allocator binding isolated memory costs.
  3. Regression Testing: After optimization, re-run system tests to verify no behavioral changes.
  4. Code Review: Changes to core subsystems (allocators, scene graph, rendering) reviewed for correctness and safety.

7. System Security and Safety Measures

7.1 Memory Safety in C++

7.1.1 Pointer Safety Mechanisms

The engine implements several pointer safety techniques:

  1. Null Checks: All public APIs validate input pointers against nullptr before dereferencing.
  2. Bounds Validation: StaticVector and array access operators include ENJINN_PERMA_ASSERT bounds checks (line 130-161 in staticVector.h).
  3. Smart Pointer Patterns: While not C++ std::unique_ptr/shared_ptr, the codebase uses owned-pointer conventions: ComponentPool owns its allocation block, Scene owns root Node, Node owns children.
  4. Ownership Documentation: Clear allocation/ownership boundaries (RuntimeContainer owns MemoryArena + FreeListAllocator) reduce orphaned pointers.

7.1.2 Bounds Checking

Example: StaticVector Bounds Check (staticVector.h, line 130) 
T& at(size_t index)
{
    ENJINN_PERMA_ASSERT(index < size_, "buffer overflow on access");
    return data[index];
}

7.2 Memory Leak Prevention

7.2.1 Guard Value Detection

The FreeListAllocator uses sentinel values (0xffffffffffffffff) stored in AllocatedBlock headers (line 27-30, freeListAllocator.cpp). On deallocation, the guard value is verified. If it doesn't match, it signals heap corruption or double-free.

Guard Value Verification (freeListAllocator.cpp, line 291) 
ENJINN_PERMA_ASSERT(allocatedBlockHeader->guard == GUARD_VALUE, 
                     "invalid free or double free");

7.2.2 Container-Level Memory Isolation

Each DLL-loaded container declares memory requirements via ContainerStaticInfo. The ContainerManager allocates a MemoryArena dedicated to that container. Explicit allocator binding/unbinding around container.update() ensures that only the container's allocator handles memory within its frame.

This architecture prevents:

  • Gameplay code leaking allocations into the runtime heap.
  • Runtime code accidentally using gameplay allocators.
  • Cross-container memory interference (each has isolated heap).

7.2.3 RAII/Cleanup-on-Exit Patterns

  1. Shader resources (glCreateProgram, glCreateShader) are freed in destructor.
  2. Container destruction calls registered cleanup functions.
  3. MemoryArena owns all sub-allocators; freeing arena frees allocators.
  4. Scene cleanup recursively destroys nodes and components.

7.3 Buffer Overflow and Heap Corruption Detection

7.3.1 Overflow Detection via Guard Values

If code writes beyond allocated block boundary, it corrupts the next block's guard value. On that block's deallocation, the assertion ENJINN_PERMA_ASSERT(guard == GUARD_VALUE) fails, and the program halts with a diagnostic message.

7.3.2 Alignment Enforcement

Memory blocks are aligned to 8-byte boundaries. During initialization, the allocator adjusts base memory pointer if needed (lines 50-60, freeListAllocator.cpp). This ensures:

  • 64-bit pointers align naturally.
  • CPU cache-line misalignment is avoided.
  • Some SIMD operations require aligned memory.

7.3.3 Fragmentation Monitoring

The calculateMemoryMetrics function reports available memory, largest contiguous block, and free block count. If fragmentation exceeds thresholds, the editor can trigger defragmentation or alert the developer.

7.4 Type Safety

  • Static Assertions: FreeBlock and AllocatedBlock struct sizes verified at compile-time (line 47, freeListAllocator.cpp).
  • Template-Based Container Safety: addComponent<T>() is type-safe; wrong component types are caught at compile time.
  • Enum-Based Flags: Request flags use enums rather than magic integers, improving correctness.

7.5 Known Limitations and Future Hardening

  1. Single-Threaded Design: Current allocator is not thread-safe (mutex stubs for Windows exist but are not used). Multi-threaded scenarios require external synchronization.
  2. No Sanitizer Integration: Could integrate AddressSanitizer (ASan) for additional runtime checks in development builds.
  3. Incomplete Input Validation: Editor and gameplay code should validate user input more rigorously (e.g., file paths, numeric ranges).
  4. DLL Loading Risk: Loading arbitrary DLLs could be exploited. Consider signing/hash verification for production use.

10. Conclusion

10.1 Project Summary

EnJinn is a custom 2D/3D game engine demonstrating sophisticated systems-level C++ engineering. Built from first principles, it showcases a professional architecture emphasizing modular design, explicit memory management, runtime extensibility, and development-time tooling. The engine addresses challenges typically hidden in commercial engines (Unity, Unreal), making it an excellent vehicle for learning advanced game engine architecture, C++17 practices, and systems programming.

10.2 Key Achievements

  • Modular Architecture: Clear separation between runtime, editor, shared contracts, and gameplay plugins.
  • Memory Ownership Model: Per-container allocators with explicit binding/unbinding, reducing cross-realm allocation bugs.
  • Scene Graph Implementation: Hierarchical node-component model supporting serialization and dynamic updates.
  • Editor Tooling: ImGui-based development environment with real-time diagnostics, scene inspection, and gameplay control.
  • Performance Optimization: Shader caching, component pooling, and frame-aware allocators minimize runtime overhead.
  • Security-Conscious Design: Guard values for heap corruption detection, bounds checking, and allocator isolation.

10.3 Technical Highlights

  • C++17 standard with modern language features (templates, move semantics, const-correctness).
  • CMake-based build system with vcpkg dependency management.
  • OpenGL rendering pipeline with GLAD loader, GLM math library, and custom shader compilation/caching.
  • DLL-based hot-reload for iterative gameplay development without full engine restarts.
  • Free-list memory allocator with fragmentation control and corruption detection.
  • Box2D physics integration with component-based entity architecture.
  • Comprehensive logging and assertion infrastructure for development-time safety.

10.4 Lessons Learned

  1. Explicit is Better Than Implicit: By controlling the update loop, allocator binding, and memory ownership explicitly, the codebase is more maintainable and debuggable than black-box engines.
  2. Layered Architecture Pays Off: Separating runtime, editor, shared contracts, and plugins allows each subsystem to evolve independently while keeping coupling low.
  3. Testing Must Be Built-In: The project initially had test infrastructure; reinstating and expanding it earlier would have caught issues faster.
  4. Documentation and Diagnostics Are Critical: Assertions, logging, and ImGui diagnostics windows provide invaluable visibility during development and debugging.
  5. Performance Requires Intent: Features like shader caching and component pooling were deliberate design choices, not accidental optimizations.

10.5 Academic and Professional Value

For students and professionals, EnJinn demonstrates:

  • How commercial engines orchestrate complex subsystems.
  • Advanced C++ patterns (RAII, polymorphism, allocator binding, template metaprogramming).
  • Systems-level programming: memory management, DLL loading, threading primitives.
  • Software engineering principles: modularity, interface design, code quality, testing.
  • Real-world trade-offs: simplicity vs. features, performance vs. maintainability, time-to-market vs. robustness.

10.6 Recommendations for Continued Development

  1. Establish Testing Discipline: Reinstate unit tests, add integration and system tests. Aim for 70%+ code coverage in critical modules.
  2. Performance Profiling: Regular benchmarking against gameplay scenarios; maintain frame-time budgets.
  3. Cross-Platform Support: Refactor platform-specific code; target Windows, Linux, macOS, and potentially WebAssembly.
  4. Documentation: API reference, architecture guides, gameplay tutorials, and design rationale documents.
  5. Community Engagement: Open-source the engine; solicit community contributions and feedback.
  6. Scalability: Design for larger teams; establish coding standards, review processes, and collaboration workflows.

10.7 Final Remarks

EnJinn exemplifies the result of combining deep systems knowledge, pragmatic engineering, and iterative refinement. While there remain opportunities for optimization and feature expansion, the architecture is solid, the code is maintainable, and the foundation supports both academic research and practical game development. The insights gained through this project—about memory management, architectural patterns, and tooling—are directly transferable to commercial engine development and broader systems programming.
